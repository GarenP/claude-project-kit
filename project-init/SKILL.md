# Project Init — the decision-discipline starter kit

You are setting up a workspace for a long-running design/build project where a human (often a non-coder) and Claude will brainstorm, decide, document, and eventually build. The kit's purpose: **nothing gets lost, nothing drifts, and verification replaces vigilance** — no rule should depend on anyone remembering it.

**THE METHODOLOGY IN ONE LINE: SPEC-FIRST, CODE-LAST.** The project runs as a long sequence of Grill Me deep-dives that fully flesh out the spec/PRD, hardened by pre-build batteries — and the *very last* thing is building the system from the finished spec, once. Design grills never write product code. This is the whole point; hold it firmly (full rule in the scaffolded process rules below).

**★ COMMANDER'S INTENT (the kit's end-state — every decision and self-improvement serves this).** *Produce a **complete, clean, buildable** spec/PRD with **as few bugs/issues as possible** when the engine is finally built — with the user **educated along the way** — and do it **as fast as that allows**, with minimal needless friction and mental load.*
**Read the order of priority carefully (this corrects a real failure mode):** completeness and correctness are the **FLOOR**; speed and low-friction **optimize WITHIN that floor — they never trade against it.** "Fast" means *don't waste the user's time or pile on needless steps* — it does **NOT** license cutting a question that matters, skipping a step that prevents a bug, or simplifying away real depth to look clean. A spec that ships fast but is shallow or incomplete is a FAILURE of this intent, not a success. When speed and completeness genuinely conflict, completeness wins and you say so. Use the intent like military commander's intent — to act on initiative without waiting for orders — but never as a reason to do less than the job needs. (Per project, the builder's own **North Star** is the commander's intent for *their* product; this is the intent for the *building process itself*.)

## Phase −1 — NEVER restart existing work; backfill any gaps (idempotency guard — check this FIRST)
Before doing ANYTHING, check whether this project is already initialized: does a `CLAUDE.md` / spec / `DECISIONS.md` / `REPO-MAP.md` / `interview-checklist.md` already exist here? **If yes, STOP the full init — do NOT re-scaffold, do NOT overwrite, do NOT restart the interview from scratch.** Switch to *continue/enhance* mode: read the existing North Star + ledger + spec, tell the user "this project's already set up — I'll pick up where you left off, not start over."

**Then run the BACKFILL CHECK against `interview-checklist.md` (this is how a skill update reaches an in-progress project).** Compare the project's checklist against the current baseline-interview question set in THIS skill. For any question that is **unanswered OR newly added since they were last here** (e.g. the kit added the UI-build-workflow question after they passed their interview), surface it now: "the kit added a couple of questions since you started — quick ones to close before we keep going," then ask them and record the answers. This is critical — without it, an existing project silently misses every interview question added in a later kit version. Only AFTER the checklist is whole do you continue their grilling. The user's project files are sacred; a skill update changes the *method* and can ADD missing questions, but never restarts or overwrites their accumulated work.

## Phase 0 — Gauge the user's level FIRST, then match it

**Assume the user knows little or nothing about product development, PRDs, databases, frontend/backend, or how any of this works.** Before the interview, open with a short conversation that gauges their understanding: have they built software before? do they know what a spec or a database is? have they used Claude Code for more than chat? Then **tailor every question and explanation to that level** — plain words, lower grade level, concrete metaphors, never engineer-to-engineer talk. The early conversations are *educational by design*: each question gets a one-or-two-sentence plain-language setup explaining **what the question is for and what the term means** before it's asked. Never fire a bare jargon question ("What's your philosophy?" / "Any quarantine needs?") — translate it first (see the per-question phrasing notes below). A technical user will tell you to speed up; a non-technical user will never tell you they're lost.

**Persist the level — it must survive every future session and every skill update.** Once gauged, write a one-line **Communication level** note into the project's `CLAUDE.md` (e.g. "Builder is non-technical — explain in plain words, no jargon without a plain definition, concrete metaphors, never engineer-to-engineer"). Because `CLAUDE.md` loads every session, this keeps the AI talking to them at their level forever — it doesn't drift back to dense tech talk, and a skill update can't erase it (it lives in their project, not the skill).

## Phase 1 — The alignment interview BEFORE scaffolding (Grill-Me style, one question at a time)

Never scaffold blind. The point of this interview is **drift-proofing**: the high-level executive focus gets extracted FIRST, and every later structure organizes toward that objective. Ask one question at a time, checkpoint every answer, and push past slogans — a real answer must be able to *reject* a future feature idea.

**Layer 1 — WHY THIS EXISTS (excavate the REAL pain — go deep, get concrete). THE MOST IMPORTANT LAYER.**
Drift happens when this stays shallow. The #1 failure mode is the AI collecting a one-line abstract answer ("make my job easier," "improve efficiency") and then building generic software that doesn't understand the person's actual problem. **Do NOT move on until you can feel the problem the way the builder feels it.** Dig like a coach, not a form:
1. **What's the actual problem — walk me through it, step by step.** Make them narrate their CURRENT reality: the specific task, day, or workflow that hurts; the exact moments that frustrate them; what they do today and why it sucks; how much time / money / sanity it costs them. Get CONCRETE and LIVED — "every morning I copy 40 work orders out of email into a spreadsheet by hand, then chase six people for status updates" — never abstract. For a personal or work tool, THIS is the job they're trying to make easier: you must actually understand their job. Ask follow-ups until it's vivid.
2. **Why are you building this — and why now?** The emotional driver. What finally pushed them to fix it. This is the fuel the whole project must keep serving; if a later feature doesn't serve this, it's drift.
3. **One sentence — and the mechanism vs. the real outcome.** Force the distinction (e.g. "the dashboard is the mechanism; getting my evenings back is the outcome"; "data collection is the mechanism; mindset change is the product"). This becomes the drift-check anchor.
4. **Who is it for?** Themselves · their team · paying customers. **If it's a product to sell:** who exactly buys it, who is disqualified (good friction — wrong buyers screened by marketing, not absorbed by engineering), and what's the moat (if methodology is the moat, an IP-protection thread opens — own-words gates, fingerprinted builds, quarantined corpus). **If it's a personal / internal tool:** who uses it, and skip the commercial framing — don't force "moat" or "disqualified buyers" onto someone building a tool for their own desk.
5. **What does success FEEL like?** The concrete after-state, in their words ("I walk in, the emails are already drafted, I approve them, I'm done by 9am"). This is the target every single feature gets tested against — and it's what you write into the project's North Star so no future session forgets it.

**Layer 2 — Commercial model (how it makes money):**
5. **How are we selling it?** Sales calls, sales page, community, partners — and what's the launch motion vs the scaled motion?
6. **DIY, DWY, or DFY — or a tier ladder of all three?** What does each tier deliver?
7. **What's the price tag?** One-time vs subscription, and is there a recurring upsell beside the product (community, support, updates)?
8. **Guarantee / refund stance?** (Including hard no's, e.g. "no deferred billing ever.")

**Layer 3 — Delivery substrate (how it ships and runs):**
9. **Where does this thing live?** Present it as levels from easiest to most complicated, with pros and cons: (a) *people download it and run it on their own computer alongside Claude Code* — simplest to build and ship, nothing for you to host, but you can't see or centrally update their copies; (b) *a website/app on the internet* (cloud services like Supabase + Vercel) — usable from any browser and you control updates, but it means servers, user accounts, security, and ongoing costs; (c) hybrids of the two. This single answer reshapes the entire architecture — settle it before any schema work.
10. **What does the customer literally receive** (folder, installer, repo) **and what must they bring** (subscriptions, accounts, hardware)? State the prerequisites honestly — they belong on the sales page.
11. **Update and support channel?** How do fixes reach sold copies?

**Layer 4 — Boundaries (what keeps it safe):**
12. **Hard constraints / non-negotiables** — e.g. "completely standalone, never wired into my other systems," "ships blank-default and must run from a fresh copy." These get ⛔ headline placement in CLAUDE.md.
13. **Quarantine needs** — explain it first: "some material helps us *design* the thing but must never end up *inside* the thing we sell — other people's books or courses, client data, your personal info. Is there anything like that here?" If yes, `_NEVER-SHIP/` + ship gates.
14. **What is explicitly NOT in v1?** Name the parked things out loud (cloud tier, telemetry, extra panels) — scope creep dies in this answer. (This question seeds the MVP scope-lock below — don't fully resolve it here, just collect the candidates.)

**Layer 5 — Philosophy (the feature-rejecting principles):**
15. **The design principles** — explain the goal before asking: "these are the 3–8 rules of taste for this product — when a cool feature idea shows up six weeks from now, these rules decide whether it gets in. Things like 'every screen pushes ONE action' or 'works on your machine forever, no internet required.' What rules like that do you already feel strongly about?" Each must be concrete enough to kill a feature idea on contact.
16. **Is there a UI — and HOW does it get built?** (Don't skip this — a real project left it unsettled and drifted.) Plain-language, two main paths with pros/cons: **(a) Built TOGETHER by Claude Code** — the same Claude Code that builds the backend also builds the frontend, so they're connected from the start. Simplest to keep in sync; best when one person/agent owns the whole thing. **(b) Built in PARALLEL by a separate design tool** (e.g. Claude on the web / a browser design tool) while Claude Code builds the backend — they're disconnected; the frontend arrives as exported snapshots (zips) that Claude Code reviews. Better visual design, but you must keep the two in sync (a protected snapshot drop zone + a conformance-skim rule each time a new snapshot lands). Settle which path; if (b), scaffold the `ui_versions/` drop zone + conformance rule. If they don't know, recommend (a) for a solo non-technical builder (fewer moving parts).
17. **Does the product itself carry AI instructions?** If yes, the dual-CLAUDE.md routing rule applies (below).

Write the answers into the scaffolded files in the same session — the interview IS the content. Layers 1–3 seed the spec/PRD skeleton (§overview, §business model, §target buyer); layers 4–5 seed CLAUDE.md.

## Phase 1.5 — MVP scope-lock (do this BEFORE scaffolding anything)

**The single biggest project-killer is scope overwhelm.** Before any structure gets built, lock the MVP — the minimum version that fixes the tool's major focus — and push everything else into later tiers. Run it as a short drill (it may take some back-and-forth; that's the point):

1. **List every capability that came up** in the interview — features, panels, integrations, automations, all of it.
2. **Apply the one test to each:** *does the core promise (the Layer-1 one-sentence purpose) break without this?* If the answer is no, it is NOT MVP — no matter how good the idea is.
3. **Sort into tiers:** **Tier 1 / MVP** = only what survived the test — the smallest thing that can be put in front of a real user and fix the main problem. **Tier 2 / Phase 2** = valuable but the promise survives without it. **Tier 3 / someday** = everything else. Good ideas don't die here — they get a *home* (the spec's tier table + the parked-threads file), which is exactly what makes it safe to exclude them.
4. **Write the tier table into the spec skeleton** and organize EVERYTHING downstream around Tier 1 only: the dependency tree's first deep-dives, the schema work, the first build target. Tier 2/3 items only get worked when they block a Tier-1 decision.
5. **Hold the line afterward.** When new ideas arrive mid-project (they will, constantly), the default routing is a ledger row + a tier assignment — not a scope expansion. Expanding Tier 1 requires the owner saying so explicitly, with eyes open.

The goal: something real, up and running, solving the main problem — as fast as possible. Momentum from a shipped Tier 1 beats a perfect plan for a Tier 3 that never starts.

## Phase 2 — Scaffold the standard kit

Create, in this order:

### 1. Project `CLAUDE.md`
Sections, IN THIS ORDER: **★ NORTH STAR (first, prominent — see below)** → ⛔ non-negotiables → design philosophy (numbered, with a **drift-check duty**: when the user floats an idea conflicting with the philosophy or a promoted decision, flag it conversationally BEFORE capturing it) → canonical-docs hierarchy (spec > schema > CLAUDE.md > process docs > brainstorms > memory; higher layer wins on disagreement) → process rules (below) → working norms.

**★ The NORTH STAR block (the anti-drift anchor — write it FIRST and PROMINENTLY at the top).** This is the fix for the most common failure: the AI forgetting WHY the project exists and drifting into generic software that doesn't solve the builder's actual problem. Built directly from Layer-1 of the interview, in the builder's own concrete words, it states: **(1) the real, lived problem** (the specific painful workflow — "every morning I hand-copy 40 work orders and chase six people"), **(2) why they're building it / why now** (the emotional driver), **(3) who it's for**, and **(4) what success FEELS like** (the concrete after-state). Because CLAUDE.md loads every session, this block re-grounds every future conversation in the real pain — keep it vivid and specific, never abstract. Pair it with the drift-guard process rule below.

Include these process rules verbatim (adapted to the project). *The scaffolded `CLAUDE.md` OWNS the always-on disciplines (answer-and-log, write-then-speak, running capture, gap-scan, paste-guard) — they apply in EVERY conversation; the **Grill Me** skill adds a deliberate interview MODE on top and REFERENCES these rules rather than restating them.*
- **★ SPEC-FIRST, CODE-LAST (hard rule — the core of this whole method).** No implementation/system code is written until the spec (`SPEC.md`/`PRD`) is **fully fleshed out** through the full sequence of Grill Me deep-dives AND has passed a **pre-build battery** while still in the design phase. **A Design Grill NEVER writes product code** — during design, "build/next steps" means more grilling and spec work, not implementation. Claude **confirms the plan/protocol before executing any big step**, and never drifts into coding because it seems helpful. The payoff of this kit comes entirely from designing thoroughly on paper first and building last, once — not from coding early and reworking. If unsure whether something counts as "building too early," stop and ask. (Scaffolding files, checker scripts, and the flow-map are PROCESS artifacts, not product code — those are fine during design.)
- **Propose-and-EDUCATE, never yes/no (the rubber-stamp fix).** "The AI proposes, the human confirms" only protects the user if they can actually judge the proposal. For a **high-stakes** confirm — anything touching their private data, security, money, or that's hard to undo — never present a bare "approve?". Instead TEACH the decision: what it is in plain words · what happens if we get it right vs. wrong (the real stakes) · your recommendation and why. So the user decides informed, and learns (on-strategy: the intent promises "educated along the way"). Routine confirms stay light — reserve the full treatment for the high-stakes ones. **And escalate honestly:** for **security architecture and legal/liability**, a wrong call is catastrophic and genuinely needs a professional — say so plainly ("I'd want a real security person / lawyer to confirm this — here's exactly what to ask them") rather than pretending a non-expert yes/no is real review.
- **Answer-and-log discipline (EVERY conversation, not only inside Grill Me):** before replying to ANY message, scan it for EVERY question/request it contains — multi-part messages routinely bury a 2nd or 3rd ask; answer them all, or explicitly PARK the ones you're deferring (never silently drop one). Carry unresolved questions forward in `brainstorms/OPEN-QUESTIONS.md` (a row per unanswered question — checked by `check_open_questions.py` at session end). Auto-log every new decision/insight to the ledger in the SAME action — never ask permission to log. *(Born from questions repeatedly dropped in long free-form back-and-forth — "carry it forward" living only in prose isn't enough; it needs an artifact + a checker.)*
- **Running capture (D-087-style — EVERY conversation, not only inside Grill Me):** any substantive work maintains a dated capture file `brainstorms/{date}-{topic}.md` holding the reasoning, context, and parking-lot — the ledger and `OPEN-QUESTIONS.md` are INDEXES that POINT INTO it. This capture is what preserves context across sessions; terse ledger rows alone aren't enough (a row records *what* was decided, not *why* or the discussion around it). Pure chatter needs no capture; substantive reasoning does. *(The full interview method for building one — checkpoint-per-answer, parking lot, cross-linking — lives in the Grill Me skill; this rule just makes the capture-file habit always-on.)*
- **Write-then-speak rule (EVERY conversation, not only inside Grill Me):** the Edit/Write that logs a decision (or a ledger row, or any captured fact) must be ISSUED and its success result IN HAND *before* any prose says "logged," "captured," "done," or equivalent. Tool call FIRST → confirm it returned without error → THEN claim it. Never write "Logged X" and then make the call; claiming a write that didn't happen is the only invisible failure mode (prose returns no feedback, so a skipped call leaves no in-context signal). Verification over vigilance: the call precedes the claim, structurally.
- **North-Star drift-guard (the anti-drift rule):** before proposing any feature, solution, or design choice, silently re-ground in the North Star — *does this actually serve the real, lived problem and the success-feeling stated there?* If a suggestion is drifting toward generic best-practice that doesn't fit the builder's specific situation, STOP and re-anchor to their actual pain (re-read the North Star; ask a concrete question about their real workflow) before continuing. The builder should never have to keep re-explaining why they're building this — the North Star holds it, and you keep checking against it. When in doubt about a direction, restate the problem in their own words and confirm before building.
- **Session start:** `git status --short` + check the ledger for PENDING rows. No build work while PENDING rows older than 7 days exist. **Re-read the North Star block — every session re-grounds in the real problem before doing anything.**
- **Decision ledger duty:** every settled decision gets a ledger row the moment it's made; idea-centric (search for an existing entry FIRST; resurfacing ideas append a ref, never a duplicate row). Contradictions of PROMOTED entries → flag to the user, then mark the old row SUPERSEDED. **Index-format rule (load-bearing):** the ledger's top index stays ONE clean human-readable line per decision (`ID | short essence | status`) — ALL granular detail (refs, rationale, sub-points, open parameters) lives in the `### D-0XX` detail block below. Never let an index cell bloat into a paragraph; if you're tempted to, the detail belongs in the detail block.
- **Repo-map duty:** any file create/move/delete updates `REPO-MAP.md` in the same action.
- **Grep-default / graph-on-demand (the retrieval routing rule).** Exact lookup / "does this exist" / logging / citations → **grep + the decisions index** (always-on, deterministic, always current — the default for ~95% of work). Relational / multi-hop / "what connects to X" / contradiction sweep / dependency tree → the **deterministic decision-graph** (parser → nodes/edges + an LLM-free viz; semantic contradiction = **Claude Code reads the related decisions on demand**). The graph is a *lens*, never the source of truth and never a blocking gate. **Standard = deterministic + Claude-Code; NO heavyweight graphRAG framework (e.g. cognee) and NO vector DB until the decision count actually makes grep too slow (YAGNI).** Where a graph must extract typed nodes from messy unstructured corpus, Claude Code (a controlled call — own the timeout/retry) or a local model emits structured JSON → load it; never an opaque auto-LLM call that can hang.
- **Root-directory hygiene + the PATHS MAP (single source of truth — what makes reorganizing SAFE).** Keep the root to TOP-LEVEL docs only (spec, CLAUDE.md, REPO-MAP, README) + the **`paths.py` map**. ALL scripts live under **`tools/`** in semantic sub-folders (`tools/qc/` checkers, `tools/hooks/` hook scripts, `tools/sync/` index+graph refresh, `tools/generators/` data gen); generated data in `data/`; never loose scripts in root — clutter accrues silently. ★ **Scaffold `paths.py` at the root — the SINGLE SOURCE OF TRUTH for every important path** (folders + key files). Every script gets its paths from it, so moving/renaming a folder is a ONE-LINE edit in `paths.py` and every script follows (critical for a non-coder reorganizing later). Scripts in sub-folders stay LOCATION-INDEPENDENT via a tiny find-root snippet that locates the repo root by a landmark file (`REPO-MAP.md`): `ROOT = next(p for p in [Path(__file__).resolve(), *Path(__file__).resolve().parents] if (p / "REPO-MAP.md").exists())` — so a script keeps working no matter which folder it's moved to. Hooks in `.claude/settings.json` reference scripts by path → update that file in the same move. **Moving any file = update `paths.py` (or the script's landmark anchor) + REPO-MAP + any hook config in the SAME action**, then verify with the checker suite + a hook fire. (Born from a real reorg — D-487/plan-004 — where hardcoded paths in 20+ scripts made moving anything scary until a `paths.py` map + landmark-anchors made it a one-line change.) Reorganize at the latest by the pre-build gate; segment old versions into an `archive/`.
- **Match the builder's environment (shell + encoding).** Detect the OS/shell and write any *saved* scripts (status lines, hooks, automation) in the builder's **native shell** — PowerShell on Windows, bash/zsh on macOS/Linux — don't assume bash. Force **UTF-8** on every file write so em-dashes, arrows (→), and symbols don't corrupt into mojibake (`â€"`, `Â§`, `â†'`); if terminal or file output shows garbled characters, STOP and re-save UTF-8 before editing on top of it (editing over mojibake worsens it). (Born from a Windows project where bash assumptions + non-UTF-8 writes produced `§`/`Â§` corruption across sessions.)
- **Commit cadence:** one commit per coherent unit (grill wrap-up, promotion sweep, schema change); Claude runs git, the user never types git commands.
- **Crash-recovery cache (continuity — nothing gets lost to a freeze):** scaffold a Stop hook (`.claude/settings.json`) + a small `cache_last_response.py` that overwrites a **gitignored `last-response.md`** with the AI's last message every turn. If the machine crashes/freezes mid-session, the next session reads that ONE file to see exactly what was last said and resume — no digging through transcript logs. It is scratch, not a history log (overwritten each turn); gitignore it and register the script + `.claude/` in REPO-MAP. (See scaffold step #6b.)
- **CLAUDE.md curation (every wrap-up):** did this session surface anything that must shape EVERY future session? Propose a 1–2 line addition, add on the user's confirm. High bar — detail lives in the spec/ledger; this file gets only the rule or the pointer.
- **Milestone reviews:** at every spec version bump / pre-build gate / pre-ship gate, run a fresh-eyes consistency review — independent agents reading the docs cold + a cross-doc agreement check. Editors can't see their own drift.
- **Battery protocol:** stress-tests = "batteries" — independent fresh-eyes agents attacking the spec through lenses the editors haven't used (simulate users · adversarial security/abuse · business ops · resource arithmetic · instruction-coherence are proven ones). Full agent transcripts ARCHIVED under `audit/` with **parent/child links between the synthesis file and the transcripts** (every conclusion traceable to its source). Keep an **experiment registry** (test types + last-run dates): try ≥1 NEW lens per battery; rerun the most useful batteries at pre-build. **Mini-battery** = ~3 agents validating one specific scenario cheaply.
- **Retrospective duty:** when a session captures a *lived conversation* worth mining — a role-played mock, a real call/interview transcript, or an unusually rich grill where an expert's reasoning ran in motion — propose running the `retrospective` skill to extract its method/signals/rules into buildable structure (plus the clarifying questions it surfaces) before the reasoning goes cold. The convergent counterpart to the battery: a battery attacks the spec for flaws; a retrospective harvests method out of a conversation.
- **Gap-scan duty (every brainstorm checkpoint):** scan for (a) unbound parameters — propose a concrete default, never a silent TBD; (b) contradictions with promoted decisions/philosophy; (c) ledger rows not updated in the same action; (d) standing-rule candidates — name them NOW with a proposed durable home, confirm with the user, write in the same action; (e) existing-home check — before proposing any new store/structure/file, SEARCH for an existing home; (f) ambiguous referents — a number/date pointing at an unnamed thing gets an open question, never a guessed binary.
- **Paste guard:** a `[Pasted text #N]` placeholder whose content didn't arrive = STOP and request a repaste immediately; never checkpoint past it; unrecovered = a permanent `LOST-INPUT` flag that blocks session completion. Long pastes → suggest file drops into `brainstorms/inbox/`.
- **Dual-CLAUDE.md routing** (only if the product ships AI instructions): the dev repo's CLAUDE.md governs build sessions; the shipped product carries its OWN CLAUDE.md. Every captured rule states which file it targets; shipped-instance content accumulates in the spec/ledger until authored at build — never lands in the dev file, and vice versa.
- **Core-structure auto-propagation:** whenever a core process structure changes (ledger format, repo-map protocol, tombstones, dependency tracking, battery protocol), update this skill's source spec in the same action — unprompted.

### 2. `brainstorms/DECISIONS.md` — the decision ledger
Header defines: **Statuses** — 🔴 PENDING (decided, awaiting promotion into the docs) · 🟡 DISCUSS (direction chosen, needs conversation to finalize) · 🎯 QUEUED-GRILL (needs its own deep-dive session) · ✅ PROMOTED (applied; target column shows where) · ⛔ SUPERSEDED (target column = the dead text to remove). **Index sorting rule:** active on top — PENDING first, then QUEUED-GRILL in dependency-tree order, then DISCUSS; completed sinks to the bottom; re-sort on every edit. **Completeness counter (header line, updated with every new row):** highest ID · total rows (active + done) · next ID — because the index is never in numeric order, the counter is how a human verifies at a glance that nothing is missing. Body: an Index table (ID · one-line decision · status) — **index cells stay ONE clean human-readable line each (`ID | short essence | status`); every piece of granular detail lives in that decision's `### D-0XX` detail block below, never crammed into the index cell** (a bloated index cell is the exact drift this rule exists to prevent) — a **Build-sequence dependency tree** (parent→child ordering of queued deep-dives, with the rule: never start a session whose upstream parent is unresolved), a PENDING sweep-queue section, then one detail block per decision (refs + promotion target).

### 3. `REPO-MAP.md` + `check_repo_map.py`
A table of every path: Path · Tag (SHIP / SOURCE / DEV / HISTORY / NEVER-SHIP) · one-line "what it is." Files in a mapped folder inherit the folder tag. Include the **new-file registration protocol**: (1) pattern-match to a folder convention → inherit, no reading; (2) small unrecognized text file → skim, one-line entry; (3) big/binary/unknown → ask the owner "what is this and why is it here?" Generate `check_repo_map.py`: walks the tree, diffs against the map, exits nonzero on unmapped/ghost entries.

### 3b. `interview-checklist.md` (the baseline-question ledger — enables update backfill)
A simple checklist listing EVERY baseline interview question (all five layers + MVP scope-lock + UI-build-workflow + dual-CLAUDE.md), each marked `[x] answered` / `[ ] open`, with a one-line note of the answer. Written during the interview and kept current. **Its job:** when a future kit version adds a new question, the Phase −1 backfill check compares this file against the skill's current question set and asks anything missing — so an already-initialized project never silently skips a newly-added question. Include a line at the top: "If the kit added questions since this was written, the AI will ask them before continuing — that's expected."

### 4. `brainstorms/` + `PARKED-THREADS.md` + `OPEN-QUESTIONS.md` + tombstones
`brainstorms/` holds dated capture files (`YYYY-MM-DD-topic.md`) + an `inbox/` for file drops. `PARKED-THREADS.md` = master recall index: a "▶ RESUME HERE" block (next action), source dumps, capture list, queued sessions, divergent thoughts, action items. **FROZEN-HISTORY tombstone convention:** every brainstorm capture opens with a banner stating it is frozen reasoning history, not build instructions — superseded decisions inside must not masquerade as current; the skill stamps this banner on every new capture automatically.

Also scaffold **`brainstorms/OPEN-QUESTIONS.md`** by copying `OPEN-QUESTIONS-template.md` (ships beside this skill) and filling in the project name — the artifact that backs the **answer-and-log discipline** (any question asked-but-unanswered gets a row; ANSWERED/DEFERRED close it). It's checked by `check_open_questions.py` (below). This is what makes "carry questions forward" a checkable fact instead of a matter of memory.

### 5. `_NEVER-SHIP/` quarantine (if Q4 said yes)
With a README stating: nothing in the product may reference paths inside it; ship-time = copying the product folder ONLY (default-deny). Add `_NEVER-SHIP/raw/` to `.gitignore` if it will hold licensed/personal data; offer a separate private backup repo for it.

### 6. Verification battery — generate all four checkers
- `check_repo_map.py` (above)
- `check_promotions.py` — reads ledger claims (PROMOTED targets, parked claims) and verifies them against the actual docs; run at session end + before every promotion-sweep commit.
- `check_grill_complete.py` — computes brainstorm-session completion (lost-paste flags, open flags, unrouted "→ route to X" arrows); must pass before a session is stamped COMPLETE.
- `check_orphans.py` — finds files referenced nowhere and not convention-covered; flag → ask the owner before registering or removing. (Convention folders include `brainstorms/`, `audit/`, `memory/`, and **`plans/`** — the standard `improve`-skill advisor-plan output.)
- `check_open_questions.py` (copy it from beside this skill) — reads `brainstorms/OPEN-QUESTIONS.md` and FAILS if any question is still `OPEN` (DEFERRED rows pass but are listed so they're never forgotten); run it at session end with the other checkers. This is the backstop for the answer-and-log discipline — a dropped question can't survive to wrap-up.
- **Format-tolerance rule (load-bearing for EVERY ledger-reading checker — see LESSONS).** Any checker that parses the ledger for decision IDs/statuses (e.g. `check_promotions`, or a project-added `check_doc_sync`) MUST tolerate every row format the ledger has historically used — the canonical `| D-0XX | … | status |` table row AND any legacy `> **D-0XX** · … Status: X.` blockquote row. A single rigid pattern silently fails valid citations to decisions written in the other format, which erodes trust in the whole battery. On PROMOTION a decision must also have a `### D-0XX` detail block (what `check_promotions` requires); never author new blockquote-format rows.

### 6b. Crash-recovery cache (Stop hook — a freeze never loses your place)
Scaffold `.claude/settings.json` with a **Stop hook** that runs a small `cache_last_response.py`: every turn it reads the session transcript, pulls the AI's last text message, and overwrites a **gitignored `last-response.md`** with it. The payoff: if the computer crashes mid-session, the next session reads that one file and picks up exactly where the AI left off, instead of the work vanishing into a transcript file nobody can find. The script reads only the hook's stdin payload (never any external system), always exits 0 (a hiccup never blocks the AI), and is DEV tooling (never ships). Gitignore `last-response.md`, register `cache_last_response.py` + `.claude/` in REPO-MAP. Born from a real session where a mid-grill freeze lost the last AI turn. (For a user who wants it across ALL projects, the same hook can go in their global `~/.claude/settings.json` instead.)

### 6c. The deterministic decision-graph layer (the relational lens) — generate when the ledger has real depth
A standard, **dependency-light** relational view over the decision ledger — the on-demand counterpart to grep (see the grep-default/graph-on-demand routing rule above). Two LLM-free pieces, generated from the ledger:
- a **parser** that reads `brainstorms/DECISIONS.md` (tolerant of every row format) + the build-sequence tree + `OPEN-QUESTIONS.md` into typed nodes (decisions/questions) + edges (`DEPENDS_ON`/`REFINES`/`ANSWERS`), pure stdlib, one-way read-only (the markdown stays canonical, the graph NEVER writes back); and
- a **viz exporter** that turns that into an interactive node-graph HTML (status/tier colored).
**Contradiction detection = Claude Code reads the related decisions on demand** and emits each clash as a `🟡 DISCUSS` recommendation (HITL — the graph proposes, the owner disposes); pair it with the deterministic doc↔ledger checker, and capture the procedure in a short `CONTRADICTION-SWEEP.md`. **Bundle the index regen + the graph regen behind ONE refresh command** (so the grep layer and the graph layer derive from the same source and can never disagree), and **run that refresh at `/finalize`** — never a heavyweight graphRAG/cognee rebuild there. The graph may also ingest the SHIPPABLE spec layer (the PRD + `docs/`) via a hard allowlist that asserts zero `_NEVER-SHIP` in its resolved file list (decision↔doc edges surface promoted-decision drift). **Do NOT reach for cognee / a vector DB / a hosted graphRAG** — at hundreds of decisions, deterministic parse + Claude-Code reasoning is faster, free, and can't hang. Add a vector index ONLY if grep genuinely stops scaling. (Born from a project that spent real effort on a brittle cognee graph whose decision-domain use case needed none of it — D-487.)

### 7. `schema/system-flow-map.md` + `.html` — GENERATE BOTH, automatically, as soon as there's a first spec
Standard artifact: sources → engines → surfaces, status-colored, built FROM the spec + ledger statuses (never from brainstorm captures), regenerated in the same commit as any spec change. **MANDATORY AUTO-TRIGGER:** the moment a first SPEC/PRD + ledger exist (i.e. right after the first grill), GENERATE BOTH FILES without being asked — this is part of scaffolding, not an on-request extra. **The `.html` MUST be built by copying the flow-map skill's bundled `template.html`** (the full interactive shape/wire/pan-zoom/tooltip/drawer engine) and populating it — NEVER a hand-rolled grid of cards (a real user got the downgraded version because the generator improvised; don't). Invoke the flow-map skill to do it correctly. **First-render reveal:** auto-open the HTML in their browser and walk them through it in plain language — the shapes, the traceable wires, the ⓘ tooltips, the click-for-detail drawer. For a non-technical owner, seeing their own system drawn and explained is the moment the architecture stops being abstract.

### 8. `ui_versions/` (if Q5 said yes)
PROTECTED drop zone for frontend snapshot zips. Never delete the newest zip; older only with explicit OK. Every new zip gets a conformance skim against the spec's locked sections; each divergence becomes a ledger row. Mid-build incongruence is EXPECTED — noted, not flagged as a problem.

### 8b. Security baseline (if the product uses AI / ingests outside data / holds sensitive data)
If the interview flagged an AI product, copy `security-baseline.md` (ships beside this skill) into the project as a standard reference, and treat its practices as defaults: read outside text in a tool-less sealed room, block outbound auto-loading of AI-produced images/links, strip trick-characters with plain code before any AI reads text, tag saved memory by trust level, lock the local server, sign + ask-before-apply for updates (security fixes free for all, features gated), monthly red-teaming on an isolated copy, and never run unvetted marketplace skills. At the pre-build gate, have a security advisor re-ground these against current attack research (the field moves fast).

### 9. `git init` + first commit
Commit the scaffold as the first coherent unit. If the user wants off-machine backup, create private remote(s) — quarantined raw data gets its own private repo, never the public one.

## Changelog discipline (when this kit itself is the project)
When working ON the kit's own skills (improving project-init / Grill Me / flow-map / battery), every shipped change gets a `CHANGELOG.md` entry in the same commit — what changed, and (where it applies) the real bug or session that prompted it. The changelog is user-facing: people pulling updates read it to know what's new and what got fixed. "Born from a real X" notes are valuable — they show the kit is battle-tested, not theorized. Keep newest-first; group by date; Added / Changed / Fixed.

## Companion skills (the kit travels as a set of five)

This skill scaffolds the *structure*; its companion skills run the *work* inside it. When sharing this kit, send all five folders to `~/.claude/skills/` (this skill plus the four below):
- **`Grill Me`** — runs the brainstorm/interview sessions with checkpointing, gap-scans, and parked-thread maintenance. The init interview above uses its method.
- **`flow-map`** — generates the interactive HTML system flow map (the standard artifact in #7).
- **`battery`** — runs the milestone stress-tests (full and mini batteries) with transcript archiving, synthesis↔transcript linking, and the experiment registry.
- **`retrospective`** — mines a captured conversation, mock, or real transcript for the method, signals, and conversation-rules inside it, producing buildable structure + clarifying questions. The convergent counterpart to `battery`: a battery attacks a spec to find flaws; a retrospective harvests the method out of a lived conversation.

Also scaffold a **spec/PRD skeleton** at the repo root from the interview: §0 document map (source-of-truth hierarchy) · §1 product overview (the one-sentence purpose) · §1a business model (tiers/pricing/guarantee from Layer 2) · §3 target buyer + disqualifiers · §parked (the explicit NOT-v1 list from Q14).

## Phase 3 — Educate, orient, and push to the next step
Scaffolding is not the finish line — a user who doesn't know what to do next will stall. End every init by, in plain language matched to their Phase-0 level:
1. **Explain what just got built and why** — each file/folder in one sentence, framed by the problem it prevents ("DECISIONS.md is the logbook so no decision ever gets lost or silently contradicted").
2. **Explain the toolkit** — each available skill, what it does, and *when to reach for it*: **Grill Me** when an idea needs to be pulled out of their head and stress-tested; **flow-map** when they want to SEE the system; **battery** at milestones when the design needs attacking by fresh eyes; **retrospective** when a captured conversation or transcript (a role-played mock, a real call/interview) holds expert reasoning worth extracting into the spec; this skill again for the next project.
3. **Walk the session loop they'll live in:** session start (git status + PENDING check) → brainstorm/grill with checkpoints + gap-scans → ledger rows same-action → promotion sweeps into the spec → checkers at session end → commit (+push) → wrap-up curation question. Remind them: the system is built so that forgetting is safe — every rule has a checker or a same-action duty.
4. **Name the next concrete action and push toward it.** Don't end with "good luck" — end with "the next thing we do is X; want to start now?" (Usually: the first deep-dive Grill Me on the biggest unresolved **Tier-1** design question — the dependency tree should already show it on top, and it's always an MVP item, never a Tier-2/3 one.)

## The final brain check (a standard, pre-build gate — for any project that ships an AI)
When the spec is fully fleshed and the project is about to be BUILT, the last thing done is one consolidated review of the **shipped system's "brain"** — the master CLAUDE.md / system prompt the product will run on: what identity it holds, what documents/indexes/tools it can access, what instructions govern it. Confirm it is complete, internally consistent, and contradiction-free, with no dead loose ends — every piece that's supposed to connect actually connects. This is the single highest-leverage review in the project: the brain is what every user interaction runs through, and a quiet error there (e.g. identity placed in conversation history instead of the system prompt, a referenced index that was never built) silently degrades everything. Run it as a fresh-eyes pass. For projects with a dual-CLAUDE.md split, this gate is specifically about the SHIPPED-instance file, assembled from everything that accumulated in the spec/ledger during the build.
